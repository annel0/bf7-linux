# USB RNDIS: хвост каждого исходящего кадра приезжал из чужой памяти

Дата: 2026-09-14. Ядро-кандидат `4.19.191-bf7-native-alps191-v1`, образ
`bf7-alps191-kernelonly.img` SHA-256
`a6235fafdb4ec7fa02467f0a3cf225244269f48324a83ad9c0b6e86e612dfe55`
(`bf7.noroot=1`: только ядро + busybox, без Debian и systemd).

**Статус: причина найдена, подтверждена на живом устройстве, исправлена в
дереве.** Первичный диагноз («передача застревает в очереди USB-гаджета»)
оказался неверным по механизму и здесь заменён.

## Симптом

Телефон → хост: мелкие пакеты проходят, полноразмерные пропадают.
Хост → телефон: работает без нареканий.

| Отправлено телефоном | Дошло до приложения на хосте |
|---:|---:|
| 500 B | 500 |
| 512 B | 512 |
| 1024 B | 1024 |
| 1460 B | **0** |
| 2048 B | **0** |

Именно поэтому скачивание файлов на телефон всё это время работало: `wget`
шлёт короткий запрос и дальше только 54-байтовые ACK, а все данные идут со
стороны хоста. 300 КБ приходили за 1.1 с с совпадающим хешем.

## Что оказалось на самом деле

Пакеты **не застревали**. Они уходили, доходили до хоста и отбрасывались
из-за неверной контрольной суммы TCP.

Замер на одной неудачной передаче 1460 байт:

```
телефон, /sys/class/net/rndis0/statistics
  tx_packets 1434 -> 1448 (+14)   tx_bytes 326127 -> 339147 (+13020)
  tx_dropped 0    tx_errors 0    tx_fifo_errors 0
хост, /sys/class/net/enp22s0f0u9/statistics
  rx_packets 1450 -> 1464 (+14)   rx_bytes 258163 -> 268999 (+10836)
  все rx_*errors = 0
хост, /proc/net/snmp
  Tcp: InErrs +7   InCsumErrors +7
```

Захват кадров сырым сокетом с самостоятельной проверкой контрольной суммы
(payload — нули из `/dev/zero`):

```
телефон->хост len=1500 eth=1514 payload=1448 cksum=0xafc0 ожидалось=0xabc0 БИТАЯ
   испорченные байты (смещение в payload, значение): [(1410,1),(1414,1),(1432,1),(1440,1)]
   смещение от начала кадра:                          [(1476,1),(1480,1),(1498,1),(1506,1)]
```

Три факта из этого захвата:

1. Испорчены **последние 38 байт** кадра, и всегда одни и те же смещения.
2. Значения — одиночные `0x01`. Расхождение контрольной суммы ровно
   `+0x0400` = 4 × `0x0100`, то есть бита ровно эта четвёрка байт.
3. В одном из кадров вместо нулей приехал ASCII `zlib@openssh` — обрывок
   давно закрытой SSH-сессии.

`0x01` на этих местах — это поля `nr_frags` и `dataref` структуры
`skb_shared_info`, которая лежит сразу за линейным буфером skb. Гаджет читал
память **за концом линейной части**.

Арифметика сходится точно: первый испорченный байт — payload+1410, то есть
skb+1520 = 44 (заголовок RNDIS) + 14 (Ethernet) + 20 (IP) + 32 (TCP) + 1410.
`skb_headlen()` был равен 1520, остальные 38 байт лежали в страничном
фрагменте и до провода не доехали.

## Причина в коде

Коммит MediaTek `3f2cec825bfe [ALPS05269737] USB: Enhance RNDIS Performance`
(Jeremy Chou, 2021-01-29) добавил две вещи:

`drivers/usb/gadget/function/u_ether.c:1212`
```c
	net->features |= NETIF_F_GSO | NETIF_F_SG;
	net->hw_features |= NETIF_F_GSO | NETIF_F_SG;
```
— после этого TCP имеет право складывать данные в страничные фрагменты, и
складывает: в 4.19 `select_size()` отдаёт линейное место только **первому**
skb в каждом `sendmsg` (`linear_payload_sz()` для остальных возвращает 0).

И разбор этих фрагментов — но **только** внутри ветки агрегации:
```c
	if (multi_pkt_xfer) {
		...
		if (net->features & NETIF_F_GSO)
			frag_cnt = pinfo->nr_frags;
		...                       /* здесь фрагменты копируются корректно */
	} else {
		length = skb->len;
		req->buf = skb->data;     /* а здесь — нет */
		req->context = skb;
	}
```

Агрегация включается только если хост в RNDIS INIT попросил
`MaxTransferSize > 2048` (`f_rndis.c:539`). Linux-хост просит ровно 2048:
`rx_urb_size = (hard_mtu + maxpacket + 1) & ~(maxpacket - 1)` = 2048. В логе
телефона это видно прямым текстом:

```
[    4.551588] rndis_command_complete: MaxTransferSize: 2048 : Multi_pkt_txr: disabled
```

Итого: на Linux-хосте агрегация выключена, работает неагрегированная ветка,
она не умеет фрагменты — и отправляет мусор. На Windows/Android-хосте
`MaxTransferSize` больше 2048, агрегация включается, фрагменты разбираются
корректно, и баг не виден. Поэтому он дожил до нас в стоковом дереве ALPS.

## Исправление

`drivers/usb/gadget/function/u_ether.c`, `eth_start_xmit()`: если пойдёт не
та ветка, которая умеет фрагменты, — выпрямляем skb.

```c
	if (!(multi_pkt_xfer && (net->features & NETIF_F_GSO)) &&
	    skb_linearize(skb)) {
		dev_kfree_skb_any(skb);
		dev->net->stats.tx_dropped++;
		return NETDEV_TX_OK;
	}
```

Проверка покрывает и вырожденный случай `sg on, gso off`, где ветка агрегации
тоже копирует `skb->len` байт из одной только линейной части.

## Подтверждение на железе

До пересборки ядра то же самое проверено в рантайме: сняты признаки
`SG/GSO/TSO` с `rndis0` утилитой `tools/bf7feat` (ethtool на телефоне не
запускается — нет `libmnl`).

```

sg = off, gso = off ->  1460 B: получено 1460, битых байт 0,  ретрансмитов нет
```

Объёмная проверка после отключения:

```

sha256 на телефоне и на хосте: a6b736b1af5d0733a24af3a66a7ca4c0c28ca1720cccb3f6161de46b1a135d26
```

И главное — **заработал SSH**:

## Проверка на прошитом ядре (без всякого обхода)

`sg = on`, `gso = on`, `Multi_pkt_txr: disabled` — ровно та конфигурация,
которая раньше ломалась:

```
1460 B: приложение получило 1460 из 1460, кадров 10, с битой суммой 0
nc,  8 МиБ: 0.25 с, 31.7 МБ/с, sha256 совпал
ssh, 8 МиБ: 0.38 с, 21.3 МБ/с, sha256 2d6a40ae... совпал
```

dropbear стартует сам: в overlay добавлены `libutmps.so.0.1` и
`libskarnet.so.2.15`, которых раньше не хватало, и `usr/sbin/bf7feat`.

Слот A остаётся `successful_boot=0` с ограниченным числом попыток, слот B —
`successful=yes`, откат на него работает.

### Побочная грабля на стороне хоста

NetworkManager держит `enp22s0f0u9` как «connected (externally)» и может
сбросить с него адрес прямо посреди передачи — тогда всё выглядит как новое
зависание. Первая же попытка скачать 8 МиБ по SSH вернула 0 байт именно
поэтому. Перед длинным тестом стоит проверять:

```sh
ip -br addr show enp22s0f0u9        # должен быть 192.168.7.1/24
sudo ip addr replace 192.168.7.1/24 dev enp22s0f0u9
```

## Что этот дефект объясняет задним числом

Одна причина стояла за всем, что мы неделю принимали за разные проблемы:

* **«Залипание» вывода telnet.** Мелкие записи шли отдельными `sendmsg` с
  пустой очередью отправки, поэтому попадали в линейную часть и доходили.
  Как только вывод становился крупнее — терялся. Телнетовский NOP-«поко»
  каждые 0.3 с помогал не тем, что «проталкивал очередь», а тем, что дробил
  поток на мелкие независимые записи.
* **Зависание SSH на KEX** у OpenSSH 9.2 и у dropbear одинаково: пакет
  `SSH2_MSG_KEX_ECDH_REPLY` большой.
* **Ложная гипотеза «CPU не просыпаются»** — её породил именно этот эффект.
* Ранняя гипотеза про «таймер зарядки» тоже была неверна; реальной причиной
  загрузки CPU был двойной `notifier_chain_register` (коммит `44cbadf68c65`).

## Инструменты, оставшиеся в дереве

* `native-linux-build/alps191-slot-test/bf7sh.py` — выполнение команд на
  телефоне через ACM-консоль: отвечает на `ESC[6n`, ждёт уникальный маркер,
  длинные и многострочные команды передаёт base64-кусками через файл,
  возвращает код возврата. Запускать под `sudo` (порт принадлежит `uucp`).
* `native-linux-build/alps191-slot-test/tools/bf7feat.c` — статический
  aarch64-бинарник, читает и снимает `sg/gso/tso/gro` через `SIOCETHTOOL`
  без ethtool и libmnl.

## Воспроизведение

```sh
# хост: слушатель, который сам считает контрольную сумму TCP
sudo python3 native-linux-build/alps191-slot-test/rxcheck.py 1460
# телефон:
head -c 1460 /dev/zero | nc 192.168.7.1 9100
```

На непропатченном ядре с Linux-хостом: приложение получает 0 байт,
`/proc/net/snmp` показывает рост `Tcp: InCsumErrors`.

## Открытый вопрос к сравнению с OEM

Дефект находится в стоковом коде ALPS, наших правок в этом файле не было,
поэтому заводское ядро BF7 почти наверняка ведёт себя так же при RNDIS-
тетеринге на Linux-хост. Проверить это на слоте B — отдельный шаг; на
результат нашей работы он не влияет, но объясняет, почему Transsion этого
не заметила (их сценарий — Windows-хост с `MaxTransferSize` > 2048).
