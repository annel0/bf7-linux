# 2026-09-11 — первый аппаратный запуск ALPS-кандидата через A/B-слот

Итог: кандидат `4.19.191-bf7-native-alps191-v1` **загружается на BF7**, дисплей
инициализируется восстановленным драйвером `td4160_hdp_dsi_vdo_hx_inx_bf7`,
suspend/resume панели работает, eMMC виден, RNDIS/ACM/HTTP-диагностика
работает. Ничего не помечено `successful_boot`; known-good `boot_b` не тронут.

## Почему не `fastboot boot`

Из `expdb` (read-only) извлечены LK-логи обеих аварийных попыток 23.08:

```
[fastboot]-[download_base:0x48b00000]-[download_size:0xcb1800]   (raw-FDT v0 probe)
[fastboot]-[download_base:0x48b00000]-[download_size:0x1093000]  (header-match v2 probe)
boot image is NULL
panic (caller 0x48029a8b): boot image decapsulate fail!
```

`0x48029a8b` = адрес возврата после `bl load_bootinfo_bootimg` внутри `cmd_boot`
(дизассемблирование `lk_b`, sha `bc59bc41…`): в fastboot-режиме work-buffer
«boot» не аллоцируется, `load_bootinfo_bootimg` игнорирует указатель на
скачанный образ и паникует на NULL. Путь закрыт для любого образа.

## Слоты

- Бэкап до изменений: `firmware-backup/live-native/pre-alps191-20260911-1704/`
  (`boot_a` 83bd274d…, `boot_b` 337a456e…, `para` ee7c9af6…).
- MTK bootctrl 2.0 в `para @0x800` (магия `BCAB`): по 2 байта на слот —
  bits0-3 priority, 4-6 tries, 7 successful.
- `fastboot set_active a` сбрасывает A в `priority 15, tries 7, successful 0`;
  `getvar` показывает кэш до `fastboot reboot bootloader`.
- Каждый проход preloader+LK списывает ~2 tries; авто-fallback на B наблюдался
  после исчерпания (A → priority 0, unbootable).
- `fastboot flash boot_a` / `set_active` — единственные записи на eMMC.

## Итерация 1 (образ 372870410…)

Загрузился, RNDIS поднялся, но `/proc/mtkfb`-путь не создался: при
`reboot()` (программный возврат через 210 с) — Oops в
`dpmgr_wait_event_timeout` ← `primary_display_suspend` ← `mtkfb_shutdown`,
`bootreason=kernel_panic` (ipanic-дамп в `expdb`). Причина найдена в OEM
`_parse_tag_videolfb` (`add x21, x0, #0x18`): у Transsion в
`struct tag_video_lfb` есть лишнее `u32` (readback панели `0x0A` = 0x9c) после
`islcmfound`, `lcmname` лежит на +24, а ALPS читал +20 → пустое имя →
`disp_lcm_probe` = NULL.

## Итерация 2 (ядро f9366fb5…, образ 5b56af0d…)

Коммит `b6fdf84f159f` в `mediatek-mt6761-alps188-gpu115`:
`struct tag_video_lfb` + `u32 lcm_status`; guard в `primary_display_suspend`.
Конфиг: `CONFIG_U_SERIAL_CONSOLE=y`; cmdline `console=ttyGS0,115200`,
`log_buf_len=16M`. Initramfs (`alps191-trial-v3/init`): ACM-функция в
composite + `getty -l /bin/sh ttyGS0`, `busybox httpd` на `:8080`
(`dmesg.txt`, `report.txt`, `cgi-bin/renew`).

Наблюдения на железе:

- `BF7 LCM: bound panel bias at I2C 0x3e`, `mtkfb_probe end` через 2.68 с;
- `/proc/mtkfb`: `LCM Driver=[td4160_hdp_dsi_vdo_hx_inx_bf7]`, 720x1612,
  `LCM Connected:Y`, `State=Alive`, `video mode + CMDQ On`, DECOUPLE;
- `echo 4 > /sys/class/graphics/fb0/blank` → экран погас;
  `echo 0` → экран вернулся (лог: `DSI_PHY_TIMCONFIG`, `ppm_lcmoff_switch`);
  это первое исполнение recovered `init_power/init` на железе;
- прямая запись в `/dev/fb0` до resume не отображалась (DECOUPLE без pan);
- eMMC: `mmcblk0` и разделы видны; `p48` монтируется `ro,noload` (по отчёту);
- хост: `cdc_acm` заблокирован `/etc/modprobe.d/99-mtkclient.conf`, обход
  `modprobe --ignore-install cdc_acm`.

Инструменты: `alps191-slot-test/monitor2.sh` (USB/RNDIS/HTTP-лизы/ACM-лог),
`acmcmd.sh` (команда через ACM с маркером), `bf7tel.py` (telnet; ненадёжен —
busybox lineedit шлёт `ESC[6n` и глотает ввод).

## Не проверено / открыто

- Тач (OVT TCM, драйвера в базе нет), Wi-Fi/ConnSys, модем, аудио, GPU.
- Долгая стабильность, тепловой профиль, suspend системы.
- Возврат в fastboot из кандидата (`reboot bootloader`) после фикса —
  проверяется отдельно.

## Дополнительно (та же сессия)

- `fbpan` (static aarch64, `alps191-slot-test/fbtool/fbpan.c`): заливка
  `/dev/fb0` + `FBIOPAN_DISPLAY` → на экране RGB-полосы. Сквозной вывод из
  ядра подтверждён; в DECOUPLE-режиме без pan-ioctl запись в fb0 не видна.
- GPU (PowerVR, DDK m1.15ED6070602 — та же строка есть в OEM Image):
  `rgx.fw`/`rgx.sh` извлечены из `firmware-backup/v2366-super/logical-a/vendor_a.img`
  (`debugfs`, хэши совпали с `docs/bf7-native/gpu.md`), положены в
  `/vendor/firmware`; открытие `renderD128` → `RGX Firmware image 'rgx.fw' loaded`,
  `Shader binary image 'rgx.sh' loaded`, VGPU/клоки включились (660 МГц), но
  `RGXPostPowerState: Polling for 'FW started' flag failed` → драйвер в bad
  state, паники нет. Открытый вопрос: тот же тест на OEM-ядре с прошивкой,
  чтобы отделить проблему порта (mfgsys/mtcmos/память FW) от платформенной.
- Возврат из кандидата: `/bin/bf7-enter-fastboot` → Preloader → LK fastboot
  `201c` (после фикса `mtkfb_shutdown`-пути); затем `fastboot set_active b`.
