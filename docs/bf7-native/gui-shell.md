# Мини-GUI shell: прототип архитектуры

`bf7-shell` — экспериментальный маленький compositor для native BF7. Он не
заменяет терминал при обычной загрузке и пока не включён через systemd.

## Граница доступа

Только `bf7-shell` открывает:

- `/dev/fb0` и выполняет `FBIOPAN_DISPLAY`;
- touchscreen и физические кнопки громкости.

Клиенты получают доступ только к Unix socket `/run/bf7-gui.sock`. Поэтому
клиент не может заблокировать raw input или одновременно рисовать в framebuffer.
Shell использует non-blocking `poll`: медленный/оборвавшийся socket-клиент
удаляется, а экран и input loop продолжают работать. Каждая команда ограничена
512 байтами, одновременно допускается не более восьми клиентов.

```text
event3 + event0 -> bf7-shell -> /dev/fb0
                         ^
                         | Unix socket
              terminal / status / future apps
```

## BF7GUI/2: граница для приложений

Это текстовые строки UTF-8, каждая заканчивается `\n`. Максимум восемь
клиентов. Один клиент владеет одной прямоугольной surface.

```text
HELLO 2 application-id
WINDOW x y width height title
COLOR RRGGBB
TEXT x y text
BUTTON id x y width height label
CLEAR
COMMIT
KEYBOARD SHOW
KEYBOARD HIDE
ORIENTATION portrait
NOTIFY info short message
PING
SHOT
```

После `HELLO 2` shell возвращает `OK BF7GUI/2 width height safe-top`; это
единственный источник геометрии, который должен использовать клиент. Старый
`HELLO name` и BF7GUI/1 пока оставлены для имеющихся приложений, но новые нужно
писать только через `bf7gui.h` / `bf7gui.c`.

Координаты `TEXT` и `BUTTON` относительны к своему `WINDOW`. Ответы — `OK` или
`ERR`. `SHOT` сохраняет уже скомпонованный кадр в безопасный путь
`/run/bf7-shell-shot-<epoch>.ppm` и возвращает этот путь — клиент не может
попросить shell перезаписать произвольный файл. После touch в surface клиент получает `EVENT TOUCH x y -`; после нажатия
на button — `EVENT BUTTON x y id`; активный клиент также получает `EVENT VOLUP`
или `EVENT VOLDOWN`.

`KEYBOARD SHOW` включает встроенную экранную клавиатуру shell и переводит
клиента в focus; `KEYBOARD HIDE` убирает её. Клавиатура не даёт приложению
доступа к input device. Символ приходит ровно focused-клиенту как
`EVENT TEXT 0 0 U+XXXX`, а служебная клавиша — как
`EVENT KEY 0 0 ENTER`, `BACKSPACE`, `ESC`, `TAB`, `UP` и т.д. Touch в зоне
клавиатуры перехватывает shell, поэтому окно под ней не получает ложные taps.

## Workspaces

Shell содержит три изолированных рабочих пространства. Нажатие на левую часть
верхней панели (`BAT`) переходит к предыдущему workspace, на правую (`WiFi`) —
к следующему; текущий номер показан как `WS1/3` в status bar. Это жесты shell,
а не команды приложения.

Окно получает workspace при запуске, а shell хранит его surface, позицию и
содержимое. При переключении остальные окна не рисуются и не получают touch,
keyboard или physical volume events, но их процессы остаются запущены. При
возврате shell показывает сохранённую surface без перезапуска. Для добровольной
экономии работы v2-клиент получает `EVENT VISIBILITY 0 0 HIDDEN` или `VISIBLE`;
это информационное событие и не даёт приложению возможности выбрать workspace.

## Notifications

`NOTIFY` — команда BF7GUI/2, а не примитив окна. Приложение может отправить
короткий текст с уровнем `info`, `warn` или `error`, но не выбирает место toast,
не рисует поверх других приложений и не получает доступа к журналу. Shell
ограничивает каждого клиента четырьмя уведомлениями в секунду и хранит последние
восемь сообщений.

Последнее уведомление показывается как глобальный toast на четыре секунды.
Касание `WSn/3` в правой части верхней панели открывает **System overview**;
касание вне него закрывает этот слой и не передаётся приложению. Левая зона
`BAT` и правая зона `WiFi` по-прежнему переключают workspace назад и вперёд.

```c
bf7gui_notify(&gui, "info", "Background task complete");
```

## System overview and lifecycle

System overview — глобальный слой shell. Он показывает три workspace, число
живых приложений в каждом, все зарегистрированные приложения и последние три
уведомления. Касание карточки workspace выбирает его. Касание работающего
приложения переключает туда; кнопка `Close` просит приложение завершиться и
посылает ему `SIGTERM`. Остановленное приложение запускается касанием строки в
текущем workspace. Приложение не получает touch, пока открыт overview.

Перед принудительным завершением v2-клиент получает `EVENT CLOSE 0 0 REQUESTED`.
`bf7gui_next_event()` преобразует его в `BF7GUI_EVENT_CLOSE`; приложение должно
закрыть socket и завершиться быстро. Shell всё равно использует `SIGTERM` как
надёжный предел, поэтому не ждёт доверенного поведения от клиента.

Socket принадлежит `root:bf7gui` и имеет права `0660`. Shell читает
`SO_PEERCRED`: root разрешён всегда, непривилегированный клиент допускается
только с primary group `bf7gui`; остальные соединения отклоняются до обработки
любой команды.

### Писать приложение

Приложение линкуется с `bf7gui.c`, а не с `bf7ui.c`: так у него физически нет
причины открывать `/dev/fb0` или `/dev/input/event*`. `bf7-hello-v2.c` — полный
минимальный пример с двумя экранами. Переход между экранами — это просто новый
набор `CLEAR` / `TEXT` / `BUTTON` / `COMMIT`; shell менять для него не надо.

```sh
gcc -O2 -Wall -Wextra -Werror -o bf7-my-app bf7-my-app.c bf7gui.c
```

Первое развёртывание v2 должно быть одной короткой, обратимой операцией: собрать
все четыре программы **на телефоне**, сохранить резервные копии только трёх
заменяемых бинарников и затем перезапустить `bf7-shell`. Файлы, которые будут
использованы: `bf7-shell.c`, `bf7ui.c`, `bf7gui.c`, `bf7gui.h`,
`bf7-keyboard-echo.c`, `bf7-keyboard-notes.c`, `bf7-hello-v2.c` и каталог
`apps/`. Пока это не выполнено, работающий shell на телефоне остаётся прежним.

Чтобы приложение появилось в launcher, достаточно положить root-owned файл
`/usr/local/share/bf7/apps/<id>.bf7app` с правами не шире `0644`:

```ini
[BF7 Application]
Id=my-app
Name=My app
Description=One-line description
Exec=/usr/local/bin/bf7-my-app
Orientation=portrait
Keyboard=true
```

Shell при старте читает эти манифесты, запускает `Exec` только напрямую (без
shell-интерпретатора) и принимает только root-owned регулярные файлы, которые
не writable для group/other. Поэтому добавление приложения не меняет shell API
и не создаёт путь к подмене бинарника через конфиг.

`Orientation=portrait` сейчас является единственным поддерживаемым режимом:
`ORIENTATION portrait` подтверждается shell, а `landscape` возвращает ошибку.
Физический разворот добавим позднее как одну атомарную транзакцию compositor +
inverse-преобразование touch, а не как доступ приложения к framebuffer.

`bf7-keyboard-echo` — маленький клиент, который не линкуется с `bf7ui` и не
открывает `/dev/fb0`, но в своей surface показывает полученные `TEXT`/`KEY`
events. Он служит наглядной проверкой маршрутизации focus → keyboard → client.

`bf7-keyboard-notes` — второй тестовый клиент: запрашивает встроенную
клавиатуру, получает socket events и сам поддерживает мини-буфер текста,
`Enter` и `Backspace`. Это проверяет, что ввод интерпретируется приложением,
а не shell.

## Уже реализовано в shell

- **Input capture.** `DOWN` выбирает surface и закрепляет touch за ней;
  последующие `MOVE`/`UP` идут тому же клиенту, даже если палец уехал за границу
  окна. `BUTTON` генерируется только при отпускании на той же кнопке.
- **Focus.** Окно, получившее `DOWN`, становится active и получает volume keys.
- **Перемещение.** Drag за title bar перемещает окно; shell не позволяет
  увести его под системную панель или за края экрана. После отпускания клиент
  получает `EVENT MOVED x y -`, где `x y` — новые экранные координаты окна.
  Active окно рисуется поверх остальных клиентов.
- **Socket backpressure.** Ответы сначала складываются в ограниченную
  per-client очередь и отправляются через `POLLOUT`. Медленный клиент не
  блокирует input/render loop; переполненный клиент отключается изолированно.
- **Системная панель.** Только shell рисует battery estimate, состояние питания,
  Wi-Fi и время; notch по центру оставлен пустым.
- **Launcher.** Фоновый shell UI строится из проверенных `.bf7app` манифестов,
  плюс System info и hardware refresh. Shell отслеживает дочерний процесс
  приложения и удаляет surface при закрытии socket.

Это ещё не window manager общего назначения: terminal пока остаётся отдельным
владельцем framebuffer и потому не запускается из launcher. Его перенос в
socket-клиент — следующий крупный этап.

## Локальный тест

Эти команды намеренно меняют только текущий экранный процесс. После теста
терминал обязательно возвращается:

```sh
systemctl stop bf7-term
systemctl start bf7-shell
/usr/local/bin/bf7-gui-demo

# вернуть штатный экран
systemctl stop bf7-shell
systemctl start bf7-term
```

`bf7-shell.service` имеет `Conflicts=bf7-term.service` и
`bf7-status.service`, поэтому systemd не позволит двум владельцам framebuffer
работать одновременно. До появления полноценного launcher'а сервис shell
оставлять отключённым (`disabled`): нормальный автозапуск остаётся за
`bf7-term.service`.

## BF7GFX/1: bitmap canvas

Для изображений и простой CPU-анимации есть отдельный Unix `SOCK_SEQPACKET`
endpoint `/run/bf7-gfx.sock`. Это намеренно **не** `/dev/fb0`: приложение
сначала открывает BF7GUI/2 окно, затем соединяется с BF7GFX из того же PID.
Shell сопоставляет его через `SO_PEERCRED`; без живого v2 GUI-соединения доступ
отклоняется.

Клиент рисует в `memfd` со стандартными пикселями `0xAARRGGBB` и передаёт
дескриптор буфера вместе с командой `FRAME` через `SCM_RIGHTS`. Shell проверяет
размеры и положение внутри окна, отображает буфер read-only, сразу копирует его
в свою память и закрывает полученный fd. На экран попадает только shell-owned
копия. Поэтому клиент не может подменить кадр после `present`, рисовать поверх
чужого окна или получить framebuffer.

Лимит одного кадра — 8 MiB, допустимый размер — не больше панели BF7. Alpha
композитится shell на CPU. `present` синхронный: ответ `OK FRAME` означает, что
копия завершена и клиент может безопасно переиспользовать свой буфер. Для
анимации достаточно повторять `bf7gfx_present()` с тем же буфером, изменяя его
между кадрами. Первый пример — `bf7-gfx-demo.c`.

```c
bf7gfx gfx;
bf7gfx_buffer frame;
bf7gfx_connect(&gfx, &gui);
bf7gfx_buffer_create(&frame, 576, 540);
/* frame.pixels[y * frame.stride + x] = 0xffRRGGBB; */
bf7gfx_present(&gfx, &frame, 24, 92); /* coordinates inside the client window */
```

## Кнопка питания и гашение экрана

Сна у этого порта нет, поэтому «выключить экран» означает ровно одно: погасить
подсветку панели (`/sys/class/leds/lcd-backlight/brightness`).

Кнопку питания раньше забирал **systemd-logind**, а у него `HandlePowerKey` по
умолчанию `poweroff`. На настольной машине это разумно, на телефоне — нет:
кнопка под пальцем, и машинальное нажатие обрывало работу. Причём с воткнутым
проводом MediaTek после выключения сразу включается обратно, и со стороны это
выглядит как самопроизвольная перезагрузка.

Теперь logind её игнорирует (`units/bf7-power-key.conf`:
`HandlePowerKey=ignore`, `HandlePowerKeyLongPress=poweroff`), а обрабатывает
сам композитор — класс `Подсветка` в `gui/main.cpp`:

- короткое нажатие гасит подсветку **и усыпляет тачскрин** (0 в `irq_en`
  драйвера `synaptics_tcm`);
- разбудить можно только кнопкой: касание не проходит, и это то, что нужно в
  кармане;
- пока экран погашен, ввод до приложений не доходит вовсе — иначе первое же
  касание ушло бы вслепую в то, что окажется под пальцем;
- яркость запоминается и возвращается та же;
- **при запуске композитор безусловно будит тач.** Иначе падение с погашенным
  экраном оставило бы сенсор мёртвым до перезагрузки, и это выглядело бы как
  поломка железа.

Сколько это экономит (телефон на зарядке, мерится ток **в батарею** — чем
больше, тем меньше потребляет аппарат; усреднение по десяти отсчётам):

    экран горит, тач слушает    92,0 мА
    экран горит, тач спит      110,5 мА
    экран погашен, тач спит    267,0 мА

То есть тачскрин сам по себе — около **18,5 мА**, подсветка — около
**156,5 мА**, вместе гашение экономит **175 мА**.
