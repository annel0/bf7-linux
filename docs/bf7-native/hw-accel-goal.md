# Задача: аппаратное ускорение для обычных программ рабочего стола

Составлено 2026-09-16 по ходу работы над браузером. Здесь записано, чего мы
добиваемся, по каким признакам поймём, что добились, и что для этого осталось.

## Цель

Обычная программа Linux, запущенная на рабочем столе телефона, должна
получать:

1. **Аппаратную отрисовку** — GL ES через PowerVR Rogue GE8300, а не
   программный растеризатор Mesa.
2. **Аппаратное декодирование видео** — H.264 через наш драйвер VA-API, то
   есть через декодер MediaTek.
3. **Нормальное окно** — рамка xfwm4, запись в панели задач, сворачивание и
   закрытие. Программа не занимает сеанс и не гасит рабочий стол.
4. **Кадр без копий процессором** — от декодера до экрана буфер ходит
   дескриптором dma-buf, а не через память.

Ключевое слово — «обычная». Не наша проба, не программа, собранная под
телефон, а то, что стоит из репозитория Debian: браузер, проигрыватель,
просмотрщик.

## Признаки готовности

Задача закрыта, когда **все** проверки проходят.

| Что проверяем | Чем | Что должно быть |
|---|---|---|
| Отрисовка | любая программа GL | `GL_RENDERER: PowerVR Rogue GE8300`, не `llvmpipe`/`swrast` |
| Отрисовка в браузере | `about:support` | «Композитинг: WebRender» **без** пометки Software; `EGL_VENDOR` не Mesa |
| Декодер виден | `about:support` | аппаратное декодирование видео числится доступным |
| Декодер работает | журнал `bf7-videod` | при проигрывании появляется «клиент подключился» и «декодер открыт» |
| Нагрузка | `top` во время проигрывания | процессор занят заметно меньше, чем при программном декодировании |
| Окно | снимок экрана X | рамка xfwm4, запись в панели задач |
| Живучесть сеанса | закрыть программу | рабочий стол на месте, перезапуск сеанса не нужен |

### Чем именно

**GStreamer** — он единственный из проверенных втягивает кадр YUV целиком,
одной внешней текстурой. mpv и Firefox разбирают его по плоскостям (R8 и
GR88), а драйвер PowerVR отдельных плоскостей дескриптором не принимает.
Почему это не лечится с нашей стороны — раздел 0 ниже, там же таблица
пробы.

    DISPLAY=:1 XDG_RUNTIME_DIR=/run/bf7-gui HYBRIS_EGLPLATFORM=x11 \
    LD_PRELOAD=/usr/local/lib/libbf7tlsguard.so GST_VAAPI_ALL_DRIVERS=1 \
    GST_GL_PLATFORM=egl GST_GL_API=gles2 GST_GL_WINDOW=x11 \
    gst-launch-1.0 filesrc location=файл ! qtdemux ! h264parse ! \
                   vaapih264dec ! glimagesink

**mpv** закрывает три признака из четырёх — с `--hwdec=vaapi-copy` он
декодирует аппаратно и рисует на PowerVR, но кадр один раз проходит через
память:

    mpv --gpu-context=x11egl --vo=gpu --hwdec=vaapi-copy файл

`LD_LIBRARY_PATH=/usr/local/lib` задавать **нельзя**: наша заглушка libOpenCL
перекрывает системную и роняет ffmpeg внутри mpv.

### Что осталось: скорость

Проигрывание идёт примерно вчетверо медленнее реального времени. Само
декодирование быстрое (с `fakesink` — тридцать кадров в секунду), упирается
согласование: клиент просит кадр сразу после подачи картинки, а конвейеру
MediaTek нужно несколько картинок вперёд. Принудительный сброс конвейера
кадр достаёт, но стоит три четверти процессора (`BF7VA_DRAIN_EACH=1`).

Это задача на производительность, а не на устройство пути.

### Добавлено 2026-09-17 19:45: драйвер больше не роняет чужой процесс

Firefox, запущенный как есть, терял процесс декодирования: `SIGSEGV` с
переходом по нулевому адресу. Виноват был наш драйвер — он звал gralloc
через libhybris там, где андроидных библиотек не видно (браузер запирает
этот процесс в пустой каталог), а libhybris при неудаче `dlsym` всё равно
делает вызов по нулевому указателю. Теперь драйвер сперва проверяет, на
месте ли андроидная часть, и при её отсутствии честно отказывает. Разбор и
стек — в журнале работ, запись 19:45.

## Что уже сделано

- **Драйвер VA-API** (`vaapi-shim`) — работает. ffmpeg декодирует аппаратно,
  30 кадров из 30, картинка совпадает с программным декодером попиксельно.
  Ставится как `pvr_drv_video.so`, libva находит его сама.
- **Платформа EGL «x11»** для libhybris — DRI3 плюс Present. Проба
  `x11gltest` выдаёт PowerVR и две тысячи кадров в секунду в обычном окне
  Xfce, с рамкой и в панели задач. То есть путь до окна X11 построен.
- **`EGL_EXT_device_query`** в нашем вендоре — через него Firefox узнаёт путь
  к узлу отрисовки. Без него его проба VA-API падала, не открыв устройство.
- **`android_wlegl`** в композиторе — родные клиенты Wayland получают
  настоящий EGL.
- **Ускоренный Xwayland** (glamor поверх нашего бэкенда GBM) — рабочий стол
  рисуется на железе.

## Что осталось

### 0. Граница: кадр без копий в mpv и Firefox недостижим

Разобрано до конца 2026-09-17. Это **не недоделка, а граница железа и чужого
кода**; закрыть её правкой нашего драйвера нельзя.

Драйвер PowerVR втягивает дескриптором dma-buf **только целые кадры**. На
прямой вопрос `eglQueryDmaBufFormatsEXT` он перечисляет
`AB30 AR24 AB24 XR24 XB24 RG16 NV12 NV21 YV12 YU12 YUYV` — однобайтового R8
и двухбайтового GR88, из которых складывают YUV по плоскостям, там нет.
Проба на живом железе (`yv12test.c`):

| дескриптор | образ | привязка |
| --- | --- | --- |
| YV12 одним слоем, 3 плоскости | создан | принята |
| NV12 одним слоем, 2 плоскости | создан | принята |
| ARGB (для сравнения) | создан | принята |
| YV12, описана только плоскость 0 | **НЕТ, 0x300c** | — |
| R8 отдельной плоскостью | **НЕТ, 0x3009** | — |

А оба проигрывателя делают ровно то, что PowerVR не умеет:

- **Firefox** (`DMABufSurfaceYUV::CreateTexture`) создаёт по образу EGL на
  каждую плоскость и передаёт при этом только атрибуты
  `EGL_DMA_BUF_PLANE0_*`. Отдать кадр целым слоем нельзя — он опишет одну
  плоскость из трёх и получит `EGL_BAD_PARAMETER`; отдать по слою на
  плоскость нельзя — слои выйдут однокомпонентные и будет `EGL_BAD_MATCH`.
- **mpv** (`dmabuf_interop_gl.c`) из составного слоя знает только NV12 и
  P010, и оба **сам разбирает на R8 и GR88**, тоже по образу на плоскость.
  Итог тот же.

Обход через RGBA проверен и тоже закрыт: у Firefox в импорте кадров VA-API
ветки RGB нет вовсе (`strings libxul.so`), а mpv через ffmpeg отказывается
ещё раньше — `h264: No usable formats for decoding!`, потому что RGBA не
входит в `VA_RT_FORMAT_YUV420`, с которым согласуется декодер H.264.

Что из этого следует: **без копий кадр берёт GStreamer** (он втягивает YUV
целиком, одной внешней текстурой), mpv закрывает три признака из четырёх
через `--hwdec=vaapi-copy`, Firefox декодирует на процессоре. Чтобы это
изменилось, править надо не нас, а libxul или mpv.

### 1. Показ без единой копии

Закрыт GStreamer'ом, см. выше. Для mpv и Firefox — граница, раздел 0.

### 2. Firefox: чего он уже добился и где стоит

Устаревшее про GLX снято. Проверено 2026-09-17 через `about:support`
(нажатием кнопки «копировать в буфер» и чтением буфера из консоли): Firefox
идёт **через наш EGL и рисует на PowerVR** — `WEBRENDER`, `X11_EGL`,
`DMABUF`, `HARDWARE_VIDEO_DECODING` числятся доступными, вендор EGL —
Imagination Technologies.

Остаётся ровно одно: кадр из декодера он взять не может (раздел 0), поэтому
декодирует на процессоре — на ролике 640×480 это почти целое ядро.

### 3. Честное ограничение: GLX

Многие программы X11 умеют только GLX. GLX у нас нет и не предвидится: это
отдельная реализация поверх нашего EGL, объём сравним со всем модулем X11.
Поэтому «любая программа» читается как «любая, которая умеет EGL» —
современные наборы инструментов умеют, старые нет. Стоит держать в уме при
обещаниях.

### 4. Мелочи для удобства

Демон `bf7-videod` стал службой (`bf7-videod.service`), андроидные службы
под ним поднимает `bf7-android-hal.service` — руками после перезагрузки
больше ничего поднимать не нужно. Осталось: демон всё ещё падает, если
клиента убить жёстко посреди декодирования.

## Чего делать не надо

Не пытаться уговорить Chromium: сборка Debian под arm64 идёт с
`disable_vaapi`, в двоичном файле нет ни `libva.so.2`, ни `vaInitialize`.
Никакими флагами это не обходится.
